# Seller OS bounded watchdog recovery

The existing watchdog could restart MCP on every HTTP timeout, then restart Tunnel again after systemd had already restarted it. A failed doctor command could add another Tunnel restart. This change bounds that recovery behavior. It does not identify or repair the Next/Turbopack HTTP stall.

The watchdog now imports the existing `CERTIFIED_CONTROLLED_RESTART_SETTLE_POLICY_V1`: 30,000 ms overall, a 5,000 ms delay between probes, at most six probes, and two consecutive full healthy reads with stable process identities and every existing runtime invariant. Slow probes consume the same overall window, so fewer than six reads can fit. The acceptance classifier retains freshness, complete evidence, exact 28-tool catalog, workspace binding, service, port and completed-watchdog checks. Transport failures cannot become acceptable evidence.

A recent service lifecycle is `INITIALIZATION_PENDING`. Its deadline is anchored to the actual lifecycle start. A controlled recovery anchors it before the restart command. Probes, observer process restarts and watchdog timer cycles cannot renew that deadline. Probe reservations survive observer termination. A completed transaction's first result is retained. Expiry becomes `STARTUP_SETTLE_EXHAUSTED`, never healthy.

The single watchdog state file is `/home/earch/.local/state/imnova-seller-os/watchdog.json`. It stores the current transaction, attempt ordinal, recovery window start, last attempt, exhausted flag and sanitized doctor/HTTP evidence. Writes use fsync and atomic rename. The existing watchdog and reporter invocations share a nonblocking flock. Missing state is initialized conservatively from all MCP starts in the preceding hour; unreadable or corrupt state fails closed. No additional service, timer, health authority or history ledger is introduced.

Automatic recovery permits **two attempts per fixed 3,600,000 ms window**, anchored at its first reserved attempt. An attempt is persisted before `systemctl restart MCP`; a failed or interrupted command still consumes it. Successful health reads and host boots do not replenish that budget. Once exhausted, timer cycles report `RECOVERY_POLICY_EXHAUSTED` and retain `LOCAL_HTTP_UNRESPONSIVE` when applicable. The next fixed window permits another bounded cycle. Clock rollback or unproven lifecycle timing prevents automatic restarts. Installation imported 26 preceding MCP starts conservatively, rather than granting a new budget in the middle of the existing storm.

The only service restart target in the installed code is MCP. The adapter verifies Tunnel's existing Requires/After relationship and relies on systemd to manage the dependent Tunnel restart. Doctor failures remain in state and sanitized journal records; they cannot directly restart Tunnel. A doctor failure alone requests full runtime verification rather than immediately restarting an otherwise responsive runtime. Full local runtime acceptance does not certify external Tunnel reachability.

Full health deliberately treats a running watchdog oneshot as degraded. Consequently, bounded observation runs through the **existing runtime-health-reporter job** after the watchdog exits. That existing transient job starts after one second with 1 ms timer accuracy and a 50-second runtime cap; its original attestation script still executes, including after recovery exhaustion. Persistent unit files, the watchdog timer schedule and dependency graph remain unchanged. These three transient reporter settings are the only operational configuration adjustments.
